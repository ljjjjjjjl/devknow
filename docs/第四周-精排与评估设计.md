## 第四周 · 精排与评估设计（rerank + 评估集）

> 目标：让检索的排序质量**可被量化**，再据此决定优化什么。
> 状态：第 4 周已完成。

### 结论速查

| 项 | 结论 |
|---|---|
| 精排模型 | `BAAI/bge-reranker-v2-m3`，SiliconFlow 的 `POST /v1/rerank` |
| 精排输入 | **两路各自 top-50 的并集**（不是 RRF 的 top-20） |
| 精排后处理 | 按 `documentId` 归并取最高分，再取 topK |
| 评估集 | 50 条：30 已知项 + 10 中文 + 10 符号 |
| 指标 | document 级 Hit@1 / Recall@5 / Recall@20 / MRR@5 / inPoolNotTop5 |
| 效果 | Recall@5 0.90 → **0.96**；符号类 0.70 → **1.00**；Hit@1 持平 0.80 |
| 代价 | 端到端 334 ms → **1372 ms** |
| 开关 | `devknow.rerank.enabled`，false 时逐位回到第 3 周行为 |

### 为什么先建评估集

第 3 周的排序质量证据只有"拿库里已有 chunk 当探针，recall@10 = 10/10"。这是拿被测系统给自己出题，测不出任何东西。

没有评估集就没有对照：精排接完只能凭感觉说"好像好了"。更要紧的是，**没有评估集就无法区分"精排没用"和"答案压根不在候选集里"** —— 这两种情况的修法完全不同（一个改排序，一个改召回）。

### 评估集构成

| 子集 | 条数 | query 来源 | 答案怎么来 |
|---|---|---|---|
| known-item | 30 | 库里 issue 标题原样 | 该 issue 本身，机械确定 |
| chinese | 10 | 手工写的中文提问 | 手工选定的权威文档页 |
| symbol | 10 | `@ConfigurationProperties`、`spring.datasource.url` 等 | 讲该特性的文档页 |

- **两个子集必须分开报**。known-item 的 query 词直接来自目标文档，词法路几乎必中，Recall@5 会接近 1.0；混进总分会把 chinese / symbol 的真实表现盖掉
- chinese 子集的意义：中文 query 对词法路零贡献（PostgreSQL 没有中文分词），召回完全由向量路承担。实测它纯靠向量路拿到 Recall@5 0.80，是 bge-m3 跨语言能力的有力证据
- 数据集放在 `src/main/resources` 下随 jar 打包，部署后仍可跑回归；代价是**改数据集必须重新打包**

### 目标答案怎么定（及其偏差）

这是整个评估里最容易出错的一步，踩了三次：

- **不能用向量路 top-1 当答案**。那是拿被测系统给自己出题，和"拿库里 chunk 当探针"是同一个毛病
- **"正文出现次数最多的前 3 个文档"不可靠**。次数并列时排序退化成按 chunk id，选出的其实是任意文档；且长 issue 的提及次数天然高于权威文档页，"出现最多"和"最相关"是两件事。实测 `logging.level` 在 5 个文档里都只出现 1 次，选出的 3 个是 id 最小的那 3 个
- **issue 与它的 PR 是同一改动的两半**。被取代的 issue 还带 `status: superseded` + `state_reason: not_planned`。只收一个 id，会把"精排把 PR 顶到第 1"判成未命中 —— 这个偏差**结构性反精排**

最终采用的口径：

- known-item：该 issue，**外加经 metadata 与标题核对过的同一改动 PR**（共 4 条）
- chinese / symbol：**讲这个特性的权威文档页**（reference / how-to），不含仅提及它的 issue

### 指标口径

全部是 **document 级**：把返回的 chunk 按 `documentId` 去重保序后，看正确文档出现在第几位。不按 chunk 级算，因为用户真正关心的是"该文档有没有被找出来"。

| 指标 | 定义 |
|---|---|
| hitAt1 | 第 1 个文档就是正确文档的比例 |
| recallAt5 | 前 5 个文档里出现正确文档的比例 |
| recallAt20 | 前 20 个文档里出现正确文档的比例（候选池覆盖率） |
| inPoolNotTop5 | 正确文档在池里但排 6~20 位的条数 —— **精排的收益上限** |
| mrrAt5 | 前 5 位内命中排名的倒数均值，第 6 位及以后记 0 |

- 不设"零命中率"：窗口 5 时它恒等于 `1 - recallAt5`，多一个字段只会让人以为是两个独立信号
- **`recallAt20 - recallAt5` 就是"精排有可能救回来的条数"**。它决定了工作量该投给排序还是召回，这个判断在第 4 周省掉了一整轮无用功

### 为什么指标截止位置必须固定

原始实现用 `mrr`，对**任意名次**都算 `1/rank`。后果：同一个答案在检索窗口 5 时算未命中（0 分），在窗口 20 时算 0.125 分。

实测两次跑批（topK 5 与 20）的 hitAt1、recallAt5 完全一致，**MRR 却是 0.8467 与 0.8502** —— 出自同一次检索的两批数据不可比。

修法：**检索窗口固定为 20，指标截止位置固定为 1 / 5 / 20**，接口不再接受窗口参数。窗口可变是这类静默失真的根源。

### 检索链路（第 4 周后）

1. 在线嵌入 query
2. 两路各取 50 个候选：向量路（余弦距离，全表扫描）+ 词法路（`ts_rank`）
3. `collect` 累加 RRF 分数 `1/(60+rank)`，同时记录 `vectorRank` / `keywordRank`
4. 精排可用时：候选池 = 两路并集 → 送 cross-encoder → 按 `documentId` 归并取最高分 → 取 topK
5. 精排不可用时：按 RRF 分数排序取 topK（与第 3 周逐位一致）
6. `enrich` 批量补 `document` 上的 title / url（对 documentId 去重，避免 N+1）

### 候选窗口的实测依据

问一个符号时，权威文档在**词法路**的名次：

| 符号 | 词法匹配 chunk 总数 | 权威文档排名 |
|---|---|---|
| `@WebMvcTest` | 53 | 第 **27** |
| `@SpringBootTest` | 95 | 第 **36** |
| `@ServiceConnection` | 45 | 第 **29** |

候选窗口是 20，这三篇全部够不着 —— **精排再准也看不到它们**。这类失败是召回问题，必须在"取候选"这一步解决。

顺带否掉了一个猜想：这些文档不是"词频低所以排后"，而是它们**只出现 1 次**而竞争 chunk 出现 2 次以上；且窗口 50 下的 `testing/spring-boot-applications.adoc` 有 8.3 万字符（是其他文档的 20 倍），长文档的片段在向量路上被稀释。

### 为什么用两路并集而不是 RRF top-N

RRF 的 `1/(60+rank)` 对"只被一路命中"的 chunk 惩罚很重：

- 词法路排 27 的 chunk 得 `1/87 ≈ 0.0115`
- 向量路排 20 的 chunk 得 `1/80 = 0.0125`

前者永远进不了融合头部。所以**提高候选数常量也没用** —— 决定名次的是 rank，不是窗口。并集绕开了这个结构性劣势，让每一路的强命中都能被精排看到。

### 为什么精排后要按文档归并

cross-encoder 对 (query, chunk) 逐个打分，**同一篇文档的多个 chunk 分数会集体偏高**。不做归并，top-5 会退化成"一篇文档的 5 个片段" —— 第 3 周被 RRF 压下去的碎片刷屏会原样回归。

归并取该文档的最高分，输出即"每个文档一条"，顺带保证了 top-5 是 5 篇不同文档。

### 降级与静默失效防护

- 精排超时、HTTP 4xx/5xx、返回条数不符 → 退回 RRF 顺序，不返回 500。检索宁可给出"次优但可用"的结果
- 响应按 `index` 还原到入参下标，与向量化按 index 重排是同一个理由：错位会让"正确维度的错误分数"排出一份看起来正常、实际语义错乱的榜单
- **所有分数都缺失时抛异常，而不是返回全 0**。全 0 会让排序退化成按 id 排，属于"看起来跑通了、排序毫无意义"的静默失效
- 部分缺失时缺失项按 0 分处理（排到最后），不因此整体降级

### A/B 结果

对照组 = 精排关闭。同一份代码、同一份数据集，只切一个开关。

| 集合 | Hit@1 | Recall@5 | Recall@20 | MRR@5 |
|---|---|---|---|---|
| overall · 关 | 0.80 | 0.90 | 0.94 | 0.8467 |
| overall · 开 | 0.80 | **0.96** | **0.98** | **0.8597** |
| known-item · 关 / 开 | 0.9667 / 0.9667 | 1.00 / 1.00 | 1.00 / 1.00 | 0.9833 / 0.9733 |
| chinese · 关 / 开 | 0.60 / 0.50 | 0.80 / 0.80 | 0.80 / **0.90** | 0.70 / 0.65 |
| symbol · 关 / 开 | 0.50 / **0.60** | 0.70 / **1.00** | 0.90 / **1.00** | 0.5833 / **0.7283** |

逐条变化：7 条改善 / 3 条退步。

- 改善：`sym-03` 15 → 4，`sym-04` 未命中 → 2，`sym-02` 9 → 5，`cn-07` 未命中 → 7，`ki-08` 2 → 1，`cn-09` 2 → 1，`sym-01` 2 → 1
- 退步：`ki-15` 1 → 5，`cn-01` 1 → 2，`cn-03` 1 → 2

**隔离实验**：精排开着、窗口压回 20，Hit@1 仍是 0.74（与窗口 50 相同）—— 证明 Hit@1 的变化来自精排判断本身，与窗口无关，两者可以独立评估。

### rerank 成本结构

由窗口 20 / 50 两组实测反推：

- 约 **470 ms 固定**（一次网络往返 + 服务端开销）
- 约 **每候选 5 ms**（cross-encoder 逐对打分）

| 配置 | 候选数 | 端到端 |
|---|---|---|
| 关精排 | 40 | 334 ms |
| 开精排 · 窗口 20 | 40 | 998 ms |
| 开精排 · 窗口 50 | 100 | 1210 ~ 1372 ms |

固定成本占大头，所以"少送几条"的收益有限；而候选数正是召回换来的，不能无限砍。

### 配置项

- `devknow.rerank.enabled` —— 开关，默认 true
- `devknow.rerank.api-key` —— 复用 `SILICONFLOW_API_KEY`
- `devknow.rerank.model` —— 默认 `BAAI/bge-reranker-v2-m3`
- `devknow.rerank.candidate-window` —— 每路候选数，默认 50（实测低于 27 会丢掉权威文档）
- `devknow.rerank.max-document-chars` —— 送精排的单条截断长度，默认 800
- `devknow.rerank.timeout-seconds` —— 默认 30

### 踩过的坑

- **两路并集会放大请求体**：100 个候选 × 800 字符 ≈ 80 KB，不是"一次轻量调用"。截断长度是控制请求体与噪声的旋钮
- **精排响应字段名必须先验证**：`relevance_score` 若与服务端不一致，全部解析为 null。返回全 0 会静默退化成按 id 排序，所以解析层对"一个分数都没拿到"直接抛异常
- **指标截止位置不固定会让两次跑批不可比**，见上文
- **标准答案的偏差是结构性的**：issue / PR / superseded issue 三类文档指向同一改动，答案集只收一个 id 会系统性低估精排
- **非交互 shell 读不到用户级环境变量**：`SILICONFLOW_API_KEY` 缺失时评估 50 条全部报错、0.17 秒返回。跑批逐条记错误而不是直接抛，才让这个失败一眼可见

### 已知问题

- **延迟 1372 ms**，其中约 1 s 是精排。质量优先的入口可接受，延迟敏感场景需关掉
- **chinese 子集 Hit@1 从 0.60 降到 0.50**，MRR@5 从 0.70 降到 0.65。精排更偏好"讨论该话题的 issue"而非"权威文档页"，对中文提问尤其明显
- **known-item 子集的目标答案仍可能有漏**：语料有 875 组标题重复的 issue，只做了 metadata 与标题核对，未逐条人工确认
- **中文 query 的词法路仍为零贡献**，需要 PostgreSQL 中文分词扩展才能修，超出本周范围
- **高频词**（`@Configuration` 覆盖 27% 语料）与第 5 名以后的相关度仍弱，精排解决不了

### 待办

- 候选池按"单路最好名次"截断：把 100 候选压到 40 左右而不丢召回，预计省 300 ms
- known-item 子集逐条人工确认目标答案，或改用可机械判定的答案口径
- 引入 nDCG 需要分级相关性标注（0/1/2），标注成本是现在这套的几倍，暂不做
- 把评估入口接进第 7 周的回归流程，每次改动后跑一遍
