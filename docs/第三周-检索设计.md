## 第三周 · 检索设计（混合检索 + RRF）

> 目标：把 8580 个 chunk 检索起来，从"数据管道"变成"可用 RAG 系统"。
> 状态：阶段 0–10 已完成。

### 结论速查

| 项 | 结论 |
|---|---|
| 检索方式 | PostgreSQL 全文检索（`ts_rank`）+ 向量双路，RRF 融合 |
| 全文检索实现 | `content_tsv` 生成列（`heading_path` 权重 A、`content` 权重 B）+ GIN 索引 |
| 向量实现 | pgvector HNSW，`vector_cosine_ops`，1024 维 bge-m3 |
| 融合参数 | 每路取 20 个候选，RRF `k=60`，等权 |
| 端到端耗时 | **~350 ms** |
| 其中在线嵌入 | **~250 ms**（网络往返，主要成本） |
| 生产入口 | `AdminController` 的 `POST /api/admin/search` |
| 临时调试入口 | `SearchProbeController`（`/api/probe/*`），仅用于阶段 9 的 A/B 对比，验收后已删除 |

> 术语：**PostgreSQL 的 `ts_rank` 不是 BM25**。它是内置的词频类排序函数，与 BM25 的 idf/k1/b 无关。作用上等价于"精确词匹配"这一路，但不是同一个算法，简历和文档里不能混用。

### 检索链路

- 查询串先过 `EmbeddingService.embedOne` 得到 1024 维向量
- 向量路：`embedding <=> CAST(? AS vector)` 取 top-20，分数为 `1 - 余弦距离`
- 词法路：`plainto_tsquery('english', regexp_replace(?, '\.', '. ', 'g'))` 取 top-20，分数为 `ts_rank`
- 两路结果按 `chunkId` 合并，`RRF = Σ 1/(60 + rank)`，同一条被两路命中则分数叠加
- 取 top-K 后按 `documentId` 去重，批量查 `document` 补 `title` / `url`

### 两条迁移

**V3 —— 加全文检索列**

- `content_tsv` 生成列，`setweight(to_tsvector('english', coalesce(heading_path,'')), 'A') || setweight(..., 'B')`
- 加 GIN 索引 `idx_chunk_content_tsv`
- 执行耗时 **7.136 秒**

**V4 —— 修点号分词**

- 重建 `content_tsv`，在生成列里对两列都做 `regexp_replace(x, '\.', '. ', 'g')`
- 执行耗时 **6.874 秒**

### 为什么 V4 必须做

- PostgreSQL 默认分词器把整条带点字符串识别成**一个 host 类 token**，例如 `org.springframework.boot.cache.autoconfigure.RedisCacheManagerBuilderCustomizer` 整条作为一个词素
- 该 token 走 `simple` 词典**不做词干化**，而查询侧的裸类名走 `english` 词典会被词干化（`customizer` → `custom`）
- 结果：**边界和词干两处都对不上，词法路返回 0 行，且完全不报错**
- 实测影响面：含 `javadoc:` FQN 的 chunk **700 条（8.2%）**；含带点标识符的 **3344 条（39.0%，上界）**
- 修法是"点号后插空格"，让每一段成为独立 token，索引侧和查询侧用**同一个表达式**

> ⚠️ 查询侧的归一化必须与 V4 生成列里的表达式**逐字一致**。V4 已执行、Flyway checksum 冻结，两处一旦漂移，词法路会整体静默失效。

### 三个 DTO 的设计决策

- `SearchRequest`：`topK` 默认 5、上限 50；不依赖 `BizException`，校验放在服务层，避免为一个 trim 引入模块依赖
- `ChunkSearchHit`：Mapper 返回类型，只含 chunk 自己的字段，不含 `title` / `url`（避免在检索 SQL 里 JOIN，JOIN 会让 LIMIT 语义含糊）
- `SearchResult`：用 `rrfScore` + `vectorRank` + `keywordRank` 三个字段，**不用单一的 `similarity`**

### 为什么是三个字段而不是一个 similarity

- 三个"相似度"量纲完全不同：向量路 `1-cosine`（0~1）、词法路 `ts_rank`（另一套）、融合后 `1/(60+rank)`（**实测只有 0.02783~0.02963，跨度 6%**）
- 用一个字段承载三者，会让人误以为可以跨 query 比较
- `vectorRank` / `keywordRank` 有真正的解释力："这条向量第 3、词法第 1，所以融合排第一"，而 `rrfScore` 只在同一次 query 内可比

### 端到端验证（6 条 query × 3 条路，top-3）

| # | query | 向量单路 | 词法单路 | RRF 融合 |
|---|---|---|---|---|
| 1 | `how to configure Redis` | Redis ×3 | Redis ×3（末条是 PR） | Redis ×3 |
| 2 | `@ConditionalOnMissingBean` | 3 条弱相关 issue | **同一篇 issue 的 3 个 chunk** | **`Bean Conditions` 第 1** |
| 3 | `Logback upgrade` | 1.5.24 ×3 | 1.5.21 / 1.5.21 / 1.5.34 | 1.5.21 / 1.5.22 / 1.5.19 |
| 4 | `如何配置数据源` | DataSource 配置 ×3 | **空** | **与向量单路逐条相同** |
| 5 | `spring.data.redis.host` | Redis ×3 | Redis ×3 | `Connecting to Redis` 第 1 |
| 6 | `integration testing` | integration-tests / Summary / Goal | Running Integration Tests / Examples / … | Running Integration Tests 第 1 |

### 四条结论

- **RRF 优雅降级（query 4）**：词法路 0 行时，融合结果与向量单路**逐条完全相同** —— 这正是"某一路没命中时另一路主导"的设计意图
- **RRF 修正多样性塌缩（query 2）**：词法单路 top-3 是同一篇 issue 的三个 chunk，融合后只保留 1 条，并把真正的文档 `Bean Conditions` 顶到第 1。**不需要额外做 documentId 限流**
- **RRF 共识机制（query 2 / 5）**：融合第 1 名不是任何单路的第 1 名，而是"两路都靠前"的结果
- **V4 归一化生效（query 5）**：同一查询在 V4 之前词法路返回 0 条，现在有 3 条

### 性能实测

| 环节 | 耗时 | 瓶颈 |
|---|---|---|
| 词法检索（GIN Bitmap Index Scan） | **0.217 ms** | — |
| 向量检索（Seq Scan） | **59.5 ~ 75.1 ms** | TOAST 页面访问 |
| 向量检索（HNSW 强制） | **77.1 ~ 114.5 ms** | CPU（图遍历） |
| 在线嵌入（query → SiliconFlow） | **~250 ms** | 网络往返 |
| RRF 融合 + 补 title/url | ~5 ms | — |
| 端到端 | **~350 ms** | |

- 原计划的"单次检索 < 200ms"不达标，但两个原因都**不是检索算法慢**
- 去掉 `WHERE c.embedding IS NOT NULL` 可省 ~15 ms（75.1 → 59.5 ms），但它只占端到端 4%，且会让 SQL 隐含依赖"库里没有 NULL 向量"，收益不值风险

### HNSW 实测结论（重要）

- `pg_stat_user_indexes` 显示 `idx_chunk_embedding_hnsw` 的 `idx_scan = 0` —— **从未被执行过**
- 强制 `enable_seqscan = off` 后确实走索引，但 **77.1 ms 比 Seq Scan 的 75.1 ms 还慢**
- IO 大幅改善但耗时没降：Seq Scan `Buffers=64164`，HNSW `Buffers=899`（少 98.6%）
- `hnsw.ef_search` 敏感性：1 → 6.2 ms / 40（默认）→ 77.1 ms / 200 → 114.5 ms。**单次扫描有约 6 ms 固定开销**，瓶颈是 CPU 不是 IO
- planner 估 HNSW 代价 `37723` vs Seq Scan `1323`，**选 Seq Scan 是正确决策**
- **索引要留着（十万级以上才体现价值），但不能声称它现在加速了检索**

> 更正一处早期结论：第 2 周末"planner 已采用 HNSW"的说法不成立。当时跑的是 `SET enable_seqscan = off; EXPLAIN (COSTS OFF)` —— 既强制了索引路径，又只计划未执行，只能证明"索引可用"，不能证明"planner 会选它"。

### 为什么 Seq Scan 要 60~75 ms

- `attstorage` 显示 `embedding` 是 `e`（EXTERNAL）—— 允许外存、**不压缩**，所以没有解压开销
- 但 PostgreSQL 的 TOAST 机制在行超过约 2 KB 时会把最大的列挪出去，**4 KB 的 vector 必然外存**
- 体积实测：`heap 9728 kB` / `toast 47 MB` / `indexes 69 MB`
- 于是 Seq Scan 每行都要去 TOAST 取 4 KB 向量，8580 行 × 约 7.5 次页面访问 = `Buffers 64164`
- **消耗的是页面访问，不是浮点运算**，这是机制决定的，改不掉

### 踩过的坑

- **中文 query 在词法路必然 0 行**：`plainto_tsquery` 用 AND 连接词素，中文词素在英文索引里不存在，整条查询被拖死。例如 `Redis 怎么配置` → `'redi' & '怎么配置'` → 0 行，连 `redi` 都匹配不到
- **带点串被当成单个 token**：见 V4 一节。这类失败是**静默的** —— 不报错、不告警，只是结构性搜不到
- **`ts_rank` 不是 BM25**：术语不能混用
- **生成列表达式必须 IMMUTABLE**：`to_tsvector(x)` 一参数形式依赖 `default_text_search_config`，是 STABLE，生成列直接建不出来；必须用两参数形式
- **`tsvector` 的 `||` 遇 NULL 会整体传播**：任一操作数为 NULL 整列就是 NULL，该行对 `@@` 永久不可见。两列都要 `coalesce`
- **`ADD COLUMN ... GENERATED ... STORED` 会重写整张表**：不像"可空无 DEFAULT 的加列"那样是纯元数据操作，8580 行实测约 7 秒
- **`DROP COLUMN` 会自动删掉依赖它的索引**，不需要 CASCADE
- **Java 文本块里的反斜杠**：SQL 需要 `'\.'` 时，Java 源码里要写 `'\\.'`
- **MyBatis 日志的 `<== Total: N` 是结果集行数不是 `COUNT` 的值**，对标量查询永远是 1
- **MyBatis 能直接把结果集映射到 record**（本项目实测无需额外配置）
- **`SearchRequest.query` 为 null 会一路走到 `List.of(null)` 抛 NPE**，表现为 500 而不是 400，校验必须放在服务层

### PowerShell / 工具链的坑（本轮新增）

- `"$var?..."` 里的 `?` 会被吞进变量名（PowerShell 变量名允许 `?`，如内置的 `$?`），必须写 `"${var}?..."`；`:` 同理
- `ConvertFrom-Json` 返回数组时不会被管道自动展开，`$r | ForEach-Object` 只迭代一次且 `$_` 是整个数组；必须用 `(curl ... | ConvertFrom-Json) | ForEach-Object` 的形式，或中间加一层 `ForEach-Object { $_ }`
- `(Get-Content $f).Count` 与 `Measure-Object -Line` 都会**低估**行数，只用 read 工具或 `Select-String` 统计
- 中文经 PowerShell 传给 psql 会 GBK 损坏，用 `U&'\XXXX'` 转义或 UTF-8 百分号编码
- 应用没启动时 `curl -s` 静默返回空，判断服务存活要看 HTTP 状态码
- PowerShell 5.1 的 `Invoke-RestMethod` 在 Content-Type 无 charset 时按 ISO-8859-1 解码，中文显示为乱码 —— 客户端问题，服务端无需改动

### 已知问题

- **PR chunk 的 `heading_path` 叶子是 PR 模板的结构性小节名**（`Approach`、`Goal`、`Summary`、`Examples`），不是主题，在 query 2 / 6 里作为噪声出现
- **叶子标题不足以标识文档**：`Redis` / `Connecting to Redis` 在 `io > caching > …` 和 `data > nosql > …` 下重复，记录结果要带 `title` + `documentId`
- **中文 query 对词法路零贡献**：跨语言完全由向量路承担
- **高频词两路都救不了**：`@Configuration` 覆盖 27% 语料，需要 rerank
- **第 3~5 名相关度偏弱**：属 rerank 阶段的工作
- **端到端被在线嵌入主导**：~250 ms / ~350 ms

### 待办

- **缓存 query 向量** —— 端到端 350 ms 里 250 ms 是在线嵌入，是唯一有数量级收益的优化点
- 引入 rerank，解决高频词与第 3~5 名偏弱
- 版本过滤（同一文档多版本时只返回最新）
